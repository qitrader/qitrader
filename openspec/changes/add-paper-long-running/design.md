## Context

模拟交易使用 OKX 公共行情 WebSocket 加本地虚拟撮合，适合在零资金风险下观察策略在真实行情中的表现。本次变更前它只能短时运行：长跑出现过两次静默失效，且缺少效果观测与日志控制手段。

第一次静默失效：`PaperGateway::cancel_order` 撤销挂单后没有释放冻结额度（`BacktestGateway` 有这段逻辑，Paper 实现时遗漏）。冻结额度随每次撤单调增，几十次撤单后本金被全部冻结，之后所有新单都因"可用额度不足"被拒，表现为策略启动一分钟后就不再交易。

第二次静默失效：WebSocket 在连接仍为 ESTABLISHED、内核接收缓冲区仍有积压数据的情况下停止向应用层推送，`read()` 一直挂起。因为没有异常抛出，重试与重连分支都不会触发，策略停摆 20 小时而重连计数始终为 0。

## Goals / Non-Goals

### Goals

- 让模拟交易可以连续运行数天而不静默停摆
- 让运行效果（净值、收益、成交、连接健康度）可被直接观测
- 让日志体积在长期运行下可控
- 修复上述两处静默失效及其诱发因素

### Non-Goals

- 不改动撮合模型本身（仍为理想化撮合，无手续费与滑点）
- 不为模拟交易引入真实交易所下单链路
- 不改变回测语义与回测绩效口径

## Decisions

### Decision 1: 看门狗用超时检测而非心跳

心跳（定期发送 ping 并等待 pong）能更早发现死连接，但需要 WebSocket 层支持主动写入并解析控制帧，改动面大。本次采用"最后一次行情时间戳 + 阈值"的超时检测：OKX 公共频道在活跃时段每秒都有推送，行情停滞超过 180 秒基本可判定异常。该方案只需在网关内维护一个时间戳，无需改动协议层。

### Decision 2: 中断挂起的读取需要协议层配合

`OkxWs::read()` 阻塞在内部 `concurrent_channel` 上，外部无法唤醒。因此给 `OkxWs` 增加 `interrupt()`，通过关闭读取通道让挂起的 `read()` 带错返回。代价是该连接不可再用，上层必须在重试分支重建连接并重新订阅——这也解释了为什么恢复逻辑放在 `watch_public` 的重试分支而不是看门狗内。

### Decision 3: 绩效统计复用回测分析器

`PerformanceAnalyzer` 已实现收益率、最大回撤、夏普比率、胜率、盈亏比。模拟交易直接复用，保证两个入口口径一致，便于横向比较。净值快照在每次周期性摘要时采集，避免逐笔采集导致数据量过大。

### Decision 4: 高频明细日志走 VLOG 而非删除

下单请求、挂撤单明细、成交明细对排查问题很有价值，但长期运行时会产生海量输出。统一改为 `VLOG(1)`：默认不写盘，需要时用 `--v=1` 或 `GLOG_v=1` 打开。累计量通过摘要中的计数器保留，不依赖明细日志。

### Decision 5: 守护与重启放在脚本层

进程守护、日志轮转、状态查看属于运维关注点，放在 `scripts/paper_service.sh` 而非程序内部，避免给交易进程增加状态机复杂度。程序只需保证自身能优雅处理 SIGTERM 并输出绩效报告。

## Risks / Trade-offs

- **看门狗阈值敏感** → 180 秒兼顾了活跃时段（每秒都有推送）与低谷时段；阈值过小会在行情清淡时误触发重连，过大则延长停摆时间。重连本身是安全的（会重新订阅），因此偏向保守取值。
- **中断后连接不可复用** → 要求重试分支必须正确重建并重新订阅，否则会永久失败。已通过重试分支的 `market_init()` + 重新订阅覆盖，并以日志确认品种数量。
- **摘要计数器溢出** → 长时间运行下计数持续增长。当前为 `int`（约 21 亿），以每分钟数百次计需数年才会溢出，暂不处理。
- **决策间隔修复会改变策略行为** → 修复后下单频率从约 1100 次/分钟降到约 65 次/分钟，是恢复到设计意图，但历史对比数据需注意口径变化。

## Migration Plan

1. 修复冻结额度释放与可用库存计算，恢复策略正常下单
2. 推进策略时钟，使决策间隔参数生效
3. 加入周期性摘要与绩效统计，建立观测手段
4. 加入行情看门狗与连接重建，消除静默停摆
5. 高频日志降级为 VLOG，控制日志体积
6. 提供守护脚本，支持长期运行与状态查看

每一步都可独立回退：前两步是行为修复，后四步是观测与运维增强，不影响策略自身的交易语义。

## Open Questions

- 是否需要把看门狗的停滞阈值与摘要间隔统一收敛到配置文件而非命令行参数？
- 长期运行是否需要按天自动生成绩效报告，而不必等到进程停止？
- 更精确的死连接检测是否值得为 WebSocket 层增加心跳支持？
